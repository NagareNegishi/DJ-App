# M5 bugfixes — self-stop label desync, loop re-arm narrowing

## What landed

Both bugs left open at the end of the `m5-deck-ui` session, found on the
Windows host checklist, are fixed. Container green: `client/build/linux`
builds clean, `ctest` 153/153 (up from 134, 19 new tests across both
units). Neither bug had automated coverage before this session. Both do
now, working around `ui/`'s lack of test linkage (below).

### Self-stop label desync (checklist step 13)

`BufferPlaybackSource` flips its internal `playing_` false on the audio
thread whenever it stops itself, whether at true end-of-track or on a
failed/absent load, but nothing read that back into `StateManager`. So
`state.playing` went stale and `DeckComponent`'s Play/Pause label stuck on
"Pause." Fixed in `EngineAdapter`: it now privately inherits `juce::Timer`, starts a 10 Hz
poll whenever a `playing: true` delta is handled and stops it on `playing:
false`, and each tick calls the new public `checkForSelfStop()`, which
applies a corrective `playing: false` local delta only when state says
playing but the engine has already stopped. The correction carries no
`positionSeconds`, matching the existing manual-pause delta shape, so the
displayed position freezes rather than jumping.

### Loop range narrows on re-arm (checklist step 10)

`DeckComponent::currentDisplayPositionSeconds()` is used both for display
extrapolation and for capturing Loop In/Out clicks, and while a loop is
active it wraps the raw position into `[in, out)`. Re-arming without
clearing first meant both new capture clicks landed inside the *old*
loop's window, a one-way ratchet that could only narrow, never widen or
relocate. Fixed with non-destructive re-arm: `onLoopInClicked()` now
stashes and clears any active loop before capturing, releasing the engine's
confinement so the new capture can land anywhere on the track. The stash is
restored on Cancel or a rejected Loop Out (`cancelPendingLoopIn()`, new),
and discarded once Loop Out actually commits a new loop.

The wrap arithmetic itself (`position >= rangeEnd` folds back into range
with `fmod`, preserving overshoot) was previously duplicated between
`DeckComponent` and `BufferPlaybackSource::getNextAudioBlock`, kept in
sync only by matching comments. Extracted to a shared, unit-agnostic,
tested pure function, `wrapPositionWithinRange` in new
`client/src/model/LoopWrap.h`, so `ui/` (seconds) and `engine/` (samples)
call the identical logic instead of parallel copies.

## Decisions

Five design-adviser findings carried a real product/UX tradeoff and went
to the user one at a time. Two more collapsed into a single dominant
option once combined with an independent simplicity finding and were
resolved without a user round-trip (noted below).

- **Self-stop correction scope**: ship unconditionally now, rather than
  gating it behind role (controller-only) or deferring it to M7's
  `PositionClock`. Recorded as an accepted risk in `docs/decisions.md`
  §7: every client corrects its own `playing` locally regardless of role,
  with no way yet to reconcile that against a room. Revisit once role
  matters, i.e. once M6/M7 land real multi-client rooms.
- **No-audio load failure**: `checkForSelfStop()` fires in that case too,
  not only true end-of-track. A `playing:true` state whose engine never
  actually started is exactly the same stale-label symptom.
- **Position on self-stop correction**: playing-only, not position. The
  existing resume-position path (`MainComponent::computeResumePositionSeconds`)
  never reads `state.positionSeconds`, so nothing currently consumes the
  now-stale value. Also recorded as an accepted risk, deferred to M7's
  `PositionClock` doing position resync properly.
- **Loop re-arm mechanism**: non-destructive re-arm (stash/restore), over
  alternatives like clamping the new capture against the old loop's bounds
  or requiring an explicit Clear Loop first. Matches how every other DJ
  tool's loop-in-point behaves: re-arming shouldn't require a separate
  clear step, and clamping would just move the ratchet rather than remove
  it.
- **Wrap-math duplication**: extract to a shared tested function rather
  than leave the two copies with a stronger "stay in sync" comment.
  `ui/` has no automated coverage at all, so this was the only way to get
  the regression test the project's testing rule requires onto logic that
  lives partly in UI code.
- Resolved without a user round-trip: an `EngineAdapter.h` wording
  ambiguity (purely editorial), and the correctness-adviser's two
  candidate fix directions for the track-change stash bug (below), which
  collapsed into one fix once combined with a simplicity finding already
  queued for the same functions.

## What the post-implementation review caught

- **Loop-arm stash survives a track change** (correctness). Loading a new
  track on a deck mid-arm-gesture left `stashedLoopOnArm_` holding the
  *previous* track's loop. Cancelling or a rejected Loop Out after the
  switch would restore that stale loop onto the newly-loaded track, a
  wrong synced write that never happened before this session's fix
  existed. Fixed by ending any in-flight arm gesture in
  `rebaseAnchorAndRefresh()` whenever `applied.trackId.has_value()`.
- **Reset scattered across call sites** (simplicity). `resetPendingLoopIn()`
  only cleared `pendingLoopInSeconds_`. Two call sites cleared
  `stashedLoopOnArm_` by hand, and a third (`onLoopClearClicked`) silently
  didn't. Folded into `resetPendingLoopIn()` itself, so every call site
  clears both fields through one call. That's what let the track-change
  fix above be a single call rather than a second field to remember.
- **Duplicated restore-the-stash sequence** (simplicity). `onLoopOutClicked()`'s
  rejected-output branch re-implemented what `cancelPendingLoopIn()`
  already did, so it now calls that directly.
- **Stale comment on `pendingLoopInSeconds_`** (docs). Said the capture is
  "not synced until Loop Out completes it," no longer true now that
  arming/cancelling over an active loop applies a synced clear/restore.
  Reworded to name `stashedLoopOnArm_` as the synced path.
- **`EngineAdapter.h`'s threading sentence overstated its own scope**
  (docs). Read as if all activity there originates from a `StateManager`
  notification. Corrected to name the `Timer` callback as the other,
  independent entry point.

All five landed in one batched fix unit. Rebuild and a full suite re-run
confirmed 153/153 green afterward.

## Risks accepted knowingly

Recorded in `docs/decisions.md` §7: self-stop correction being role-blind,
`state.positionSeconds` staying stale after a self-stop correction, and
`StateDelta::loop`'s continued inability to express "armed but not
confining" (why the loop re-arm stash has to live in private
`DeckComponent` state rather than something the shared model or other
clients could see).
