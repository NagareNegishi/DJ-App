# M5 — Single-deck UI (real)

## What landed

`DeckComponent` in `client/src/ui/`, replacing the M3/M4 dev UI in
`MainComponent`: play/pause, position slider, gain, rate, and loop
in/out/clear controls, all writing through `StateManager::applyDelta`.
`TrackListComponent` gained a double-click callback so loading a track no
longer needs a separate button. Container green: `client/build/linux`
builds clean, `ctest` 134/134 (unchanged: this milestone adds no automated
tests, covered below). CI's `format` job was already flipped to required in
a prior session (`30b993b`), so M5's third task was already satisfied before
this session started.

## Why no automated tests for this milestone

`dj-app-tests` links `dj-app-core`, which deliberately excludes anything
needing `juce_gui_basics`. `juce::Component` subclasses can't be compiled
into the test binary at all. `docs/plan/05-testing.md`'s required-suites
list has no `ui/` entry, and M2's `TrackListComponent` already shipped with
zero unit tests under the same constraint. `blackbox-tester` and
`whitebox-tester` were both skipped for this reason rather than spawned to
find nothing to do. Verification for this milestone is the build, the
existing suite staying green, and the host checklist.

## The design problem this milestone had to solve

The plan calls for a 30 Hz playhead timer, but the class meant to own live
position extrapolation (`state/PositionClock`) doesn't arrive until M7, and
building it now would count as implementing ahead of the milestone.
`DeckComponent` instead holds a small local "anchor" (position + timestamp +
rate snapshot) and extrapolates from it every frame, re-basing the anchor on
every `StateManager` notification for its deck rather than only on explicit
seeks. That distinction is the whole fix for two bugs a pre-implementation
`design-adviser` pass caught in the first draft of this spec: pausing
snapped the displayed position backward to the play-start point, and any
gain/rate/loop click during playback did the same. Both traced to the same
root cause: treating "last written `positionSeconds`" as the anchor instead
of "wherever the extrapolation already said the playhead was." The fix
re-derives the anchor from `currentDisplayPositionSeconds()` itself before
overwriting it on a non-position-bearing delta, so nothing ever discards
already-correct extrapolated state. These findings were surfaced to the user
before implementation started, along with a simpler alternative: drop live
extrapolation for this milestone entirely. The user chose the full fix.

Loop capture is a two-click gesture (Loop In arms a local pending point,
Loop Out completes it) because `StateDelta::loop` only has three states
(absent, explicit null, or a complete pair), with no slot for a lone
in-point. Resume-after-pause still needs one narrow exception to "UI never
touches `engine/`": `MainComponent` (the composition root, where that
exception has always lived) injects a `resumePositionProvider` closure into
`DeckComponent`, so the self-stop-at-end-of-track detection first fixed in
M3 (`73075b9`) and again in M4 stays in one place without `DeckComponent`
itself including `engine/`.

## What the post-implementation review caught, and what happened to it

- **Load didn't reset position** (correctness, medium). The load delta
  carried `trackId` but not `positionSeconds`, so loading a second track
  left the model, and therefore the new deck's anchor, holding the previous
  track's stale position, even though the engine itself resets to 0 on
  load. Fixed by setting `positionSeconds = 0.0` on the load delta.
- **Timer fought the user's drag** (correctness, medium). The 30 Hz timer
  unconditionally overwrote the position slider's value, including
  mid-drag, which could make a released seek land somewhere other than
  where the user let go. Fixed by skipping the timer's update while
  `positionSlider_.isMouseButtonDown()`.
- **Duplicated position-display logic** (simplicity, medium) and
  **duplicated loop-cancel reset** (simplicity, low). Both call sites
  extracted into single private helpers (`updatePositionDisplay()`,
  `resetPendingLoopIn()`).
- **Change-log-style comment** (docs, medium). A comment in
  `computeResumePositionSeconds()` cited a commit hash and referenced the
  now-deleted M3/M4 dev UI. Reworded to state the invariant directly.
- **Top-of-file comment overstated the write-back rule** (docs, medium).
  `DeckComponent.h` claimed every user gesture writes through `applyDelta`,
  contradicting the Loop In field's own comment a few lines down. Reworded
  to name the Loop In/Out exception explicitly.
- **Missing rate-slider center-detent** (spec completeness, caught
  independently while checking a docs-adviser out-of-scope note, not itself
  an adviser finding). `docs/plan/04-client.md` requires a center-detent at
  1.0 for the rate slider. The implementation, copied from the old dev UI's
  wiring per this unit's own spec, never had one in either version. Fixed
  with `setDoubleClickReturnValue(true, 1.0)`. JUCE has no built-in
  drag-snap detent, so double-click-to-reset is the standard idiom for
  "quick return to a value."

All seven landed in one batched fix unit. Rebuild and a full suite re-run
confirmed green afterward.

## Unresolved risk

Host checklist (`docs/plan/checklists/M5-host.md`) run on Windows
2026-08-06: build clean, `ctest` 0 failures, steps 1-15 all pass except two
bugs found (step 12's zero-length-loop edge case was skipped as not
reproducible at human click speed — already covered by
`StateManagerTest.cpp:445`). M5 is **not** closed; both need to be resolved
and the affected steps re-verified before recording M5 in `PROGRESS.md`,
per this project's milestone-discipline rule.

- **End-of-track Play/Pause label desync** (step 13). When a track plays to
  its natural end, the button stays labeled "Pause" instead of flipping to
  "Play," even though the engine has stopped. The first click after
  end-of-track is silently absorbed resyncing the label only (no audio
  effect, treated as a pause action while already stopped); a second click
  is needed to actually restart from 0. Likely cause: `DeckComponent`'s
  play/pause label only updates in its own toggle handler, not in reaction
  to a `StateManager` notification when the engine self-stops — the same
  class of issue as the self-stop handling fixed in M3 (`73075b9`) and
  again in M4, reappearing in this milestone's new `DeckComponent` in a
  different spot (label sync rather than resume position).
- **Loop range narrows on re-arm** (step 10, discovered opportunistically).
  Capturing a new Loop In/Out while a previous loop is already active,
  without clicking Clear Loop first, produces a narrower range than the
  clicked points would suggest; clearing first avoids it. Not yet
  determined whether this is a bug or intended behavior (e.g. the second
  Loop In implicitly clamping against the still-active loop's own bounds) —
  needs a design read before deciding on a fix.

Both are queued for a follow-up `build-orchestration` session rather than
fixed inline here.
